# Design iterations

An iteration is one product/design change, recorded as a folder under `iterations/`. It is a
product/design iteration, **not** an app release — releases are the `package.json` version and
`CHANGELOG.md`.

How an iteration is planned and built: [docs/design-workflow/process/README.md](../docs/design-workflow/process/README.md);
every step with the questions to answer: [iteration-guide.md](../docs/design-workflow/process/iteration-guide.md)
(`/be-iteration` walks it with you). There is no shared index file — `pnpm iteration:list` is the
index.

## Naming

`iterations/<type>-<topic>-<YYYY-MM-DD>-<id>/`

| Part | Rule |
| --- | --- |
| `<type>` | `launch`, `feat`, `change` or `fix` |
| `<topic>` | lowercase kebab-case words, no digits. `launch` has no topic: `launch-<YYYY-MM-DD>-<id>` |
| `<YYYY-MM-DD>` | the day the iteration was opened |
| `<id>` | four random lowercase letters, so names stay unique across people |

Examples: `launch-2026-09-30-jxmr`, `feat-pharmacy-returns-2026-10-06-kqzx`. There is only ever one
launch. The date is a value (when the iteration was opened) and the only part that carries digits.

The same name is used in clinozy-fe and clinozy-be. Create the folder only in the repository the
change touches; `pnpm iteration:new <type> <topic> --both` creates it in both.

**One shared plan, the backend owns the contract.** Under `--both` there is one plan of the
contract, here: `plans/routes-final.md`, `route-changes.md`, `db-changes.md`, `worker-changes.md`
and the decisions that shape them. The frontend's plan links to them and adds only its own part
(screens, states, copy) — never a second copy of a route, a field or a rule. A change the frontend
needs in the contract is a request to this plan, decided here.

## The folder

| Path | Holds | Written by |
| --- | --- | --- |
| `README.md` | the field table, then a `## History` list | `iteration:new`, then only the commands |
| `intake-files/` | **what arrived** — files received from outside, exactly as delivered, flat, never edited; the iteration's snapshot resolves from it (see Intake modes) | `iteration:intake` |
| `KICKOFF.md` | the plan and its ordered ROUTE ledger | be-iteration-planning |
| `plans/` | our supporting documents: `decisions.md`, `coverage.md`, `db-changes.md`, `route-changes.md`, `worker-changes.md`, `routes-final.md` (the route review, confirmed sub-domain by sub-domain — [template](../docs/design-workflow/process/routes-final-template.md)), `requirements/`, `features/`, `acceptance.md`, `frontend-route-map.md` (for the frontend: the contract changes, each design operation's route, every route — generated by `pnpm iteration:frontend-map` — and the design features dropped; written at Close) | be-iteration-planning (+ scope decisions during implementation; the route map at Close) |
| `AS-BUILT.md` | per ROUTE row: planned · actually built · difference · why · decision · commit; revisions to upcoming rows; a closing summary; the **Standing deviations** | be-kickoff-iteration |

- **`intake-files/`** stores only what arrived (see Intake modes). The iteration's **snapshot** is
  resolved from it: for an `overlay`, or a `brief` on a named Baseline, the Baseline's snapshot (up
  the Baseline chain) with these files laid over it. Backend mandatory set, checked on the resolved
  snapshot: `PRD.md`, `schema-routes.md` (+ `BRIEF.md` in brief mode) — a brief from scratch needs
  only `BRIEF.md`; optional: `design-overview.md`, a carried-forward `BRIEF.md`. It is locked once
  the Status is `approved` or later — re-recording the hash included.
- **`AS-BUILT.md` › Standing deviations** is the complete list of where the code differs from the
  drop. The launch starts it empty; each iteration copies its Baseline's list, adds what it
  deliberately builds differently and removes what it resolves. Planning reads it, so a later
  iteration plans against what was actually built.
- **`plans/db-changes.md`**, **`plans/route-changes.md`** and **`plans/worker-changes.md`** are the
  iteration's database changes (the Mermaid data diagrams), its proposed routes and its background
  work — one file each, kept current at every planning step with before → after for anything that
  changes (each `requirements/` file ends with the same before → after table), so they can be
  reviewed without a PR diff; frozen at approval. `pnpm db:viewer` draws
  `db-changes.md` in plan mode (the iteration as Latest + its changes) while the iteration is not
  `frozen`; kickoff confirms each proposed route and records any change in `AS-BUILT.md`.
- **`KICKOFF.md`** is frozen at approval: afterwards only its ROUTE Status column and
  "revised → AS-BUILT #n" markers change.
- `schema-routes.md` is the same file, byte-for-byte, in the same-named clinozy-fe iteration —
  `pnpm iteration:list` shows its fingerprint in both repositories.

## README fields

| Field | Value |
| --- | --- |
| Type | `launch`, `feat`, `change` or `fix` |
| Process | `full`, or `lite` — a `fix` planned in one step (`iteration:new fix <topic> --lite`); a README without the row is `full` |
| Topic | the kebab-case topic; `—` for launch |
| Owner | the person driving it (`git config user.name`) |
| Opened | `YYYY-MM-DD` |
| Branch | the branch it is built on |
| Baseline | `none` — from scratch, the default for every iteration — or an earlier iteration the user named (incremental) |
| Status | `planning`, `ready-for-approval`, `approved`, `implementing`, `done` or `frozen` |
| Summary | one line on what it changes — the one field you write by hand |
| Drop placed | the day `iteration:intake` placed the drop |
| Drop source | where the drop came from |
| Intake mode | `full`, `overlay` or `brief` — how the snapshot was built |
| Intake note | what was received versus carried forward: `<n> received`, `<n> received (<names>) · <m> carried forward from <baseline>`, or `1 received (BRIEF.md) · from scratch` |
| Schema-routes | the first 12 characters of the sha256 of the resolved snapshot's `schema-routes.md` |
| Intake hash | the first 12 characters of one sha256 over the whole resolved snapshot — any added, removed or edited file changes it, in this iteration's `intake-files/` or anywhere up its Baseline chain |

Below the table, a `## History` list records every Status and Baseline change, one line each:
`- <date> · <from> → <to> · <reason or —> · <git user.name>` (a Baseline change reads
`Baseline <from> → <to>`). The commands write every table value and the History — never edit those by
hand — except **Summary**, the one line you write yourself after `pnpm iteration:new`.

## Mode and Baseline

- **Baseline `none` → MODE initial** — the default: every iteration opens from scratch and takes
  no earlier iteration or its files into account.
- **MODE incremental** only when the user names a Baseline ("build on <iteration>"), recorded with
  `pnpm iteration:baseline`. Nothing suggests or asks for one.
- The incremental delta is the designer's "What changed" notes **plus**
  `pnpm iteration:diff <baseline> <iteration>`, which compares the two iterations' resolved intakes
  **only** (never the README, `KICKOFF.md`, `plans/` or `AS-BUILT.md`). The Baseline's
  `intake-files/` is therefore mandatory: `iteration:baseline` refuses a Baseline whose resolved
  snapshot lacks the required set, and `iteration:diff` refuses an iteration without `intake-files/`
  or whose snapshot cannot be resolved. Anything the diff shows that the notes omit is a finding.
- Parallel branches are fine. Before merging, if another iteration reached `main` meanwhile, check
  overlap — the same entity, route or screen changed by both — and resolve it in review.

## Intake modes and the gate

`pnpm iteration:intake <iteration> <source> --mode <mode>` stores **what arrived** in
`intake-files/` and checks the snapshot it resolves to; `<source>` is a folder or a single file.

| Mode | What arrived | `intake-files/` stores | The snapshot (resolved) |
| --- | --- | --- | --- |
| `full` (default; always the launch) | the whole drop | the drop as received | what it stores |
| `overlay` | only the changed files | the received files | the Baseline's snapshot with them laid over it (at least one file; nothing is removed) |
| `brief` | only a written change, `BRIEF.md` (template: `tooling/iterations/templates/BRIEF.md`) | `BRIEF.md` | from scratch (Baseline `none`): `BRIEF.md` alone; on a named Baseline: its snapshot plus `BRIEF.md`, and any other received file must match the Baseline's byte for byte |

- **The resolved snapshot.** Every command reads an iteration's snapshot, never its folder alone —
  the gate, the Intake hash, `iteration:diff`, `iteration:list` and the Baseline checks. An
  `overlay`, or a `brief` on a named Baseline, takes each file it does not store from its Baseline,
  whose snapshot may in turn come from its own Baseline. Baselines are frozen, so the snapshot never
  moves underneath; a Baseline chain that loops, or reaches an iteration without `intake-files/`,
  fails the gate.
- `overlay` needs a confirmed Baseline (not `none` or `—`) whose intake passes the gate; so does a
  `brief` on a named Baseline. A `brief` on Baseline `none` starts from scratch — its whole
  mandatory set is `BRIEF.md`.
- A `BRIEF.md` must have the sections What changes · Why · Affected screens, entities and routes ·
  Rules · Acceptance criteria · Out of scope — "none" is an answer, a missing section is not.
- Replacing a different existing snapshot (removals included) needs `--replace`, only while
  planning. From `approved` on, any change is refused.
- `--both` builds the sibling's same-named iteration in the same mode on **its own** Baseline, with
  `PRD.md` and `schema-routes.md` (+ `BRIEF.md` in brief mode) from this snapshot.
- **Compacting.** Intakes placed before this rule stored a copy of every Baseline file.
  `pnpm iteration:intake <iteration> --compact [--dry-run]` removes each stored copy that is byte
  for byte the Baseline's and keeps what was received (the names in the Intake note). The resolved
  snapshot and its Intake hash stay the same — the command refuses otherwise, and refuses a `full`
  intake or a brief from scratch, which have nothing to compact — so it works at any Status, a frozen
  iteration included, and never writes the README.

**The gate**, `pnpm iteration:intake <iteration> --check [--baseline <baseline>]`, proves the
mandatory set is in the resolved snapshot and the recomputed Intake hash equals the README's (for
the Baseline too), and that an overlay, or a brief on a named Baseline, was built on the README's
Baseline (a brief from scratch was built on none). It exits 1 with
"Gate failed — 1 problem." (or "— 2 problems.", and so on) and "Stop here: write nothing, change no
status.", then one line per problem with its fix. Planning and kickoff run it first and stop when
it fails.

The Intake hash is one sha256 over every file of the resolved snapshot — names in code-unit order,
each fed as its name, a NUL, its bytes and a NUL — cut to 12 characters; it is computed the same way
in both repositories, so a `full` intake's hash is the hash of its flat, visible `intake-files/`.

## Lifecycle

Status moves one step at a time with `pnpm iteration:status <iteration> <status>`:

| Status | Set by | When |
| --- | --- | --- |
| `planning` | `pnpm iteration:new` | the folder is opened; the drop is placed and planned |
| `ready-for-approval` | be-iteration-planning | `KICKOFF.md` and `plans/` pass the self-check |
| `approved` | the user's go-ahead | logged in `plans/decisions.md`; `KICKOFF.md` and `intake-files/` freeze |
| `implementing` | be-kickoff-iteration | the user confirms the iteration to kick off |
| `done` | be-kickoff-iteration | every ROUTE row is closed, `plans/acceptance.md` filled, `AS-BUILT.md` summarized |
| `frozen` | the last commit before the merge | the iteration merges to `main` |

A **lite** fix (Process `lite`) moves `planning → implementing → done → frozen`: be-iteration-planning
writes `KICKOFF.md`, `plans/decisions.md` and `plans/acceptance.md` in one step and stops once for the
user's go, and be-kickoff-iteration then moves it to `implementing`, where its intake locks; it may go
back to `planning` from `implementing` or `done`, with a reason.

`ready-for-approval`, `approved`, `implementing` or `done` may go back to `planning` with
`--reason "<why>"` — `done` when work the user finds still open goes back into the same iteration
before it is frozen; nothing else is allowed. Never edit a frozen iteration — a correction is a new
`fix` iteration.

## Commands

```bash
pnpm iteration:new feat pharmacy-returns --both          # open (README only)
pnpm iteration:new fix rounding --lite                   # a fix planned in one step
pnpm iteration:intake <iteration> <source> [--mode full|overlay|brief] --both   # store what arrived
pnpm iteration:intake <iteration> --check [--baseline <baseline>]                 # the gate
pnpm iteration:intake <iteration> --compact [--dry-run]                           # drop stored copies of the Baseline's files
pnpm iteration:baseline <iteration> <baseline|none>      # record the confirmed Baseline
pnpm iteration:diff <baseline> <iteration> [--json]      # the delta: the two resolved intakes only
pnpm iteration:frontend-map <iteration> [--check]        # plans/frontend-route-map.md section 3: every route
pnpm iteration:status <iteration> <status> [--reason "<text>"]
pnpm iteration:list   # Name · Type · Owner · Opened · Baseline · Status · Intake mode · Schema-routes · Intake hash · Drop placed
```

Every command takes `--help`. `iteration:new` and `iteration:intake` take `--dry-run`; `--both` works
on the same-named folder in the sibling repository (`--sibling <path>` overrides where it is).
