# Design iterations — clinozy-be

Claude Code loads this file when it works in `iterations/`. It holds sections moved out of the root [`CLAUDE.md`](../CLAUDE.md), which keeps a pointer to each; the root rules apply here too.

## Design iterations

A design iteration is one product/design change, recorded as `iterations/<type>-<topic>-<YYYY-MM-DD>-<id>/` (type `launch` · `feat` · `change` · `fix`) — not an app release. Rules: **`iterations/README.md`**; the flow: **`docs/design-workflow/process/README.md`**; every step with its questions: **`docs/design-workflow/process/iteration-guide.md`**. **`/be-iteration [iteration]`** walks it with the user.

The folder: `README.md` (field table + History, written by the commands — except the Summary line you write) · `intake-files/` (**what arrived** — Intake mode `full`, `overlay` or `brief`; the snapshot resolves from it up the Baseline chain — locked from `approved`; `--check` is the gate) · `KICKOFF.md` (the plan + ROUTE ledger, written by planning, frozen at approval) · `plans/` (decisions, coverage, `db-changes.md` + `route-changes.md` + `worker-changes.md` — the data diagrams, proposed routes and background work, kept current at every step with before → after for changes, reviewed at each step's review — requirements, stories, acceptance) · `AS-BUILT.md` (what each ROUTE row actually built, written during implementation, ending with the Standing deviations carried to the next iteration).

**Before opening one, ask (AskUserQuestion — never guess):** what changes, in one line (the Summary) · launch, or `feat` / `change` / `fix` · the topic (lowercase kebab-case, no digits) · backend only or both repositories (`--both`) · is the current branch `<type>/<topic>` · what arrived — the whole drop, only changed files, or only a `BRIEF.md` (the Intake mode) · and, only if the user says so, what it builds on (the Baseline is `none` unless the user names one, which must have its own `intake-files/` — never suggest one).

**Then follow the steps one by one — finish and check each before the next:**

1. **Branch** — `git switch -c <type>/<topic>`.
2. **Open** — `pnpm iteration:new <type> [topic] [--both] --dry-run`, check the name (Baseline `none`), then run it (README only, Status `planning`); write the Summary.
3. **Place the drop** — `pnpm iteration:intake <iteration> <source> [--mode full|overlay|brief] [--both] --dry-run`, then for real: what arrived in `intake-files/` (`full` the whole drop; `overlay` the changed files, laid over the Baseline's snapshot; `brief` a `BRIEF.md` — from scratch, or added to a named Baseline's snapshot), the Drop, Intake and Schema-routes rows filled; check it with `pnpm iteration:intake <iteration> --check`.
4. **Plan, no code** — "plan iteration `<iteration>`" → **be-iteration-planning** Steps 0–7 (Step 0 confirms the iteration — and records a Baseline only if the user names one, `pnpm iteration:baseline` — then the gate `pnpm iteration:intake <iteration> --check` — stop if it fails; incremental delta = `pnpm iteration:diff <baseline> <iteration>` — the resolved intakes only — plus the designer's notes, or `BRIEF.md` in brief mode; the Baseline's Standing deviations; RED questions to the user; Step 5 the route review — `plans/routes-final.md` from `docs/design-workflow/process/routes-final-template.md`, one folder per sub-domain with its nested sub-domains inside, each confirmed by the user) → `KICKOFF.md` + `plans/` → `ready-for-approval`.
5. **Approve** — the step reviews are the plan's review of record, so the user confirms them and what changed since the last one → `pnpm iteration:status <iteration> approved` (or back: `planning --reason "<why>"`).
6. **Kick off** — "kickoff iteration `<iteration>`" → **be-kickoff-iteration** Step 0 confirms, runs the gate → `implementing`; then **one ROUTE row at a time**: do (NEW table → `docs/getting-started/staged-build-prompt.md`; CHANGE table, flow, background work → `/be-build-requirement`) → verify → the `AS-BUILT.md` row → impact check (scope change → stop and ask) → the user's review — the row's review of record, its `Reviewed` cell in `AS-BUILT.md`; the PR's review covers only what changed after it. **The plan proposes; agent-os decides:** the backend's agent-os (skills, rules, agents) is the expert — whenever the plan and agent-os disagree or anything is unclear, agent-os wins, and it may change the plan's names, types, paths or job details on the way — record each difference in `AS-BUILT.md` and sync it back into `plans/db-changes.md`, `route-changes.md` and `worker-changes.md`. A route review (`plans/routes-final.md`) is built **ditto** — where agent-os cannot build it as written, stop and ask; the agreed change goes into the review first.
7. **Close** — the gates, `/be-pre-merge-review` (review only), `plans/acceptance.md` filled, the `AS-BUILT.md` summary, the frontend's route map (`plans/frontend-route-map.md` — sections 1, 2 and 4 by hand, section 3 by `pnpm iteration:frontend-map <iteration>`) → `pnpm iteration:status <iteration> done`.
8. **Freeze** — resolve overlaps with iterations merged meanwhile → `pnpm iteration:status <iteration> frozen` in the last commit → the user raises the PR.

Under `--both` there is **one shared plan**: this repository's `plans/` own the contract (routes-final, routes, tables, background work); the frontend's plan links to them and adds only its screens. The frontend kicks off as soon as `plans/routes-final.md` carries its **Route review final** line (every sub-domain confirmed), without waiting for this plan's approval.

A small `fix` can run **lite** (`pnpm iteration:new fix <topic> --lite`, README Process `lite`): be-iteration-planning plans it in one step — `KICKOFF.md`, `plans/decisions.md` and `plans/acceptance.md`, one stop for the user's go — and be-kickoff-iteration moves it `planning → implementing → done → frozen`, with no `ready-for-approval` or `approved`.

Status changes only through `pnpm iteration:status` (one step forward along `planning → ready-for-approval → approved → implementing → done → frozen`, a lite fix `planning → implementing → done → frozen`; back to `planning` only with `--reason`) — it also signs the README's History. Never edit a merged iteration; a correction is a new `fix` iteration.

## Iteration commands

- `pnpm iteration:new <type> [topic] [--both] [--sibling <path>] [--lite] [--dry-run]` — open a design iteration `iterations/<type>-<topic>-<YYYY-MM-DD>-<id>/` (type `launch|feat|change|fix`) with its README only and Baseline `none` (from scratch; `pnpm iteration:baseline` records one the user names); `--both` opens the same folder in clinozy-fe; `--lite` (a fix only) records Process `lite`. Model: **`iterations/README.md`**
- `pnpm iteration:list` — every iteration's Name, Type, Owner, Opened, Baseline, Status, Intake mode, **Schema-routes** (first 12 characters of the sha256 of the resolved snapshot's `schema-routes.md`, to compare with clinozy-fe's), **Intake hash** (`<live> ≠ README <recorded>` when the snapshot changed) and Drop placed
- `pnpm iteration:status <iteration> <status> [--reason "<text>"]` — move an iteration one step along `planning → ready-for-approval → approved → implementing → done → frozen` (a lite fix: `planning → implementing → done → frozen`), or back to `planning` with `--reason`; writes the README's Status and a History entry
- `pnpm iteration:intake <iteration> <source> [--mode full|overlay|brief] [--both] [--replace] [--dry-run]` — store what arrived in `intake-files/` (never README.md) and check the snapshot it resolves to: `full` = the drop as received (always the launch), `overlay` = the received files, resolved over the Baseline's snapshot, `brief` = `BRIEF.md` (template `tooling/iterations/templates/BRIEF.md`), from scratch on Baseline `none` or over a named Baseline's snapshot; check the mandatory set on the resolved snapshot (`PRD.md`, `schema-routes.md`, + `BRIEF.md` in brief; a brief from scratch: `BRIEF.md` alone); fill Drop placed / Drop source / Intake mode / Intake note / Schema-routes / Intake hash; replace only with `--replace` while planning, locked from `approved` on; `--both` builds the sibling in the same mode on its own Baseline. `pnpm iteration:intake <iteration> --check [--baseline <baseline>]` is the gate; `pnpm iteration:intake <iteration> --compact [--dry-run]` removes an older overlay's or brief's stored copies of its Baseline's files, never changing the snapshot or its hash
- `pnpm iteration:diff [<baseline>] <current> [--json]` — compare two iterations' resolved intakes only (both `intake-files/` mandatory): files, screens, PRD / schema-routes / prototype changed, schema-routes entities, fields, enums, routes and operations; then the raw `git diff --no-index`
- `pnpm iteration:baseline <iteration> <baseline|none>` — record the Baseline the user confirmed (an earlier iteration in this repository with a complete `intake-files/`, or `none`); writes the row + a History line
- `pnpm iteration:frontend-map <iteration> [--check]` — regenerate section 3 of the iteration's `plans/frontend-route-map.md` (every route: gate, idempotency, team-only, route review number, OpenAPI summary) from `docs/routes.txt`, the OpenAPI document and `plans/routes-final.md`, keeping the hand-written sections; a missing map starts from `tooling/iterations/templates/frontend-route-map.md`; `--check` fails when it is stale; a frozen iteration is refused
